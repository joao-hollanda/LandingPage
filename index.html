01 · Arquitetura
Clean Architecture, com as setas certas

Passe o mouse (ou toque) nas camadas. As setas são as referências reais entre os projetos da solution — o Domain não depende de ninguém.

Learnly.Domain
zero dependências

Entidades, enums e exceções de domínio — usuários, planos, simulados, redações e social. O núcleo não conhece banco, HTTP nem IA.

02 · Fluxo do simulado
Da resposta ao feedback, sem desperdiçar token
  1. POST /api/simulado sorteia questões por disciplina
  2. PUT /api/simulado/responder/{id} corrige e calcula a nota
  3. ObterOuGerarExplicacoes() reaproveita explicações já geradas; só as que faltam vão para a IA, todas numa chamada
  4. GerarFeedbackAsync() feedback geral do desempenho
  5. PostgreSQL persiste nota, feedback e explicações
Decisão: a explicação de cada questão é gerada uma vez e reaproveitada por todos os alunos. Menos chamadas, menos custo, sem esbarrar no rate limit do provedor.
03 · Mentor com function calling
A IA consulta e ajusta o plano do aluno

O mentor não só conversa: ele chama ferramentas do backend com os dados reais do aluno. O usuarioId é injetado pelo servidor — o modelo nunca escolhe de quem são os dados.

04 · Post-mortem
IDOR em produção: como fechei a classe inteira de bug
o problema Endpoints recebiam o usuarioId pela rota. Qualquer usuário logado podia trocar o número na URL e ler planos e simulados de outra pessoa.
a correção Criei o BaseController.GetUserId(): o id sai só do JWT. As rotas perderam o {usuarioId} e todo recurso buscado por ID ganhou checagem de dono.
depois Rate limiting por IP e por usuário, JWT com refresh endurecido, security headers e segredos fora do repositório.
lição Validar em cada endpoint é checklist; tirar o dado do alcance do cliente é design. Prefiro o segundo.
